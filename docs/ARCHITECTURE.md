# 模块职责与依赖

PurrAI 是单进程 Python 服务与可选 Vue 后台。业务模块按职责拆分，应用入口负责组装，数据库变化由 Alembic 迁移管理。

广告审核的 `AdvertisementReviewer` 负责组装和实时任务协调，`advertisement_intake.py` 负责接收消息和本地样本匹配，`advertisement_context.py` 在已校验的会话内准备近期证据和请求内容，`advertisement_decisions.py` 负责证据复核与处置，`advertisement_history.py` 独立处理历史样本。实时和历史审核共用 `advertisement_model.py` 的模型请求、预算结算与协议校验；历史复核仍只更新样本，不处罚成员。频道与样本处罚共用证据记录和删除任务生成，保留各自的任务去重键、处罚与学习条件。

积分设置通过 `PointsAdministration` 保存，HTTP 层不操作设置表。积分奖励与人工调整共用 `PointsLedger.apply_delta` 的余额范围检查、版本递增和流水写入，各入口保留各自的重复请求、权限和版本检查。积分、抽奖和群菜单管理均只接收 `AdminContext`，不持有 `Management`。

Bot 的具体按钮操作和文本输入由对应业务面板处理，业务注册只在 `BotPanels` 组装，重复注册在启动时明确报错；中央路由只接收群访问能力，负责分发、交互状态和导航恢复。前端普通查询使用 `useLatestRequest`，它与预览共用只依赖 Vue 的 `useRequestScope` 处理并发和销毁；预览工具不依赖工作台或会话。过期或销毁后的请求不会更新页面、触发失败回退或清除新会话。预览仍在草稿修改时立即作废，读写任务共用 `combineTasks` 合并加载和错误状态；不影响本地编辑的辅助查询保持不阻塞编辑。启动查询可将原始错误交还调用方，其他页面保留各自的分页回退和草稿保护。

## 应用入口

`app.py` 和 `runtime.py` 负责组装依赖。`Service`、`Management`、`BotAdmin` 保留原有调用入口，内部只组装或委托具体模块，不再承载数据库查询、处罚决策或面板内容。业务模块不能反向导入这三个入口。

| 入口 | 职责拆分后的实现 |
| --- | --- |
| `service.py` | `member_events.py` 处理成员加入、离开和身份变化；`verification.py` 处理验证输入与期限；`moderation.py` 处理消息审核；`actions.py` 领取并派发任务 |
| `management.py` | 配置、成员处置、规则与白名单、群接入、归档、聊天和系统维护分别由对应的 `*_admin.py` 或 `group_configuration.py` 实现 |
| `bot_admin.py` | `bot_state.py` 保存交互状态；`bot_ui.py` 处理 Telegram 传输；不同业务的 `bot_*_panels.py` 展示面板；输入、命令、按钮路由和回调分别处理 |

`Management` 的 `service` 位置参数和 `chat` 属性只为既有 Python 调用兼容保留。业务实现不持有 `Service`，生产运行时通过构造参数明确传入聊天服务与群访问服务。CLI 批准群时不再创建整套运行服务。

`Runtime` 只组装运行组件并保留 `persist`、`process_one`、`start`、`stop` 和健康状态入口。`UpdateReceiver` 负责长轮询、接入筛选、归档与收件及轮询位置的原子保存；`InboxProcessor` 负责通道领取、同群顺序、验证输入屏障和处理失败后的重试；`TelegramEvents` 负责 SDK 事件适配及有界的验证按钮回执；`WorkerSupervisor` 负责常驻任务重启、故障状态和停止。组件通过事件集合、派发函数和当前事件上下文连接，不持有 `Runtime`。

## 后端业务边界

`GroupAccess` 统一群接入和当前 Telegram 管理员身份检查，供管理操作和归档发送共同调用。任务处理器不再创建 `Management` 来检查资格，消除了原来的反向依赖。

`ActionRunner` 管理领取、顺序、失败和重试，将实际操作派发给验证、成员限制、自动处罚及通知处理器。`action_transport.py` 保留网络请求前后的状态重查；`action_execution.py` 保留短事务与外部请求之间的交接。拆分没有把网络请求搬进数据库写锁。

聊天和审核的纯计算通过 `PolicyExecution` 先提交可恢复的准备状态、释放 SQLite 写锁，再交给工作线程。计算完成后重新读取群、规则、来源消息和相关状态；变化会使旧结果失效并重试。领取任务时只有成功提交后才登记忙碌范围，交接异常会释放本次预留。待审聊天积分奖励使用独立顺序，不占用签到与查询的通知顺序。

每个 `ActionHandler` 明确登记执行方法、业务检查和是否需要额外核实成员身份。`ActionPreparation` 只装载共同数据、检查群接入、人工决定和限制身份，并协调权限核实；验证状态、截止时间与发送计时由 `VerificationActions` 负责，解除限制的来源核实由 `RestrictionActions` 负责，历史昵称任务的批次要求由 `AutomaticActions` 负责。任务运行器不再根据验证状态或具体处罚类型作决定。

`member_decisions.py` 持久保存每个成员最新的人工处置编号。新决定在同一事务中取消旧的待执行人工任务，旧失败任务也不能通过重试覆盖新决定；网络请求返回后继续核对该编号。延迟重试的任务保留自己的成员通道，不阻塞其他成员。时间戳相同时使用 SQLite 插入顺序排序，避免 Windows 连续写入时由随机编号决定先后。人工任务在实际执行和发起 Telegram 修改前核实操作者当前权限，权限查询暂时失败时保留任务重试；发送意图在这些只读检查完成后、真正请求 Telegram 前保存。

任务领取先通过执行时间索引筛选，再通过同一排序范围的前序任务检查保持原先的成员、通知和菜单顺序。`queue_scope` 是由任务现有字段计算的内部列，0040 为已有库增加该列及索引；它不进入管理接口或操作证据。未来的自动恢复任务仍不占用当前成员的操作顺序，聊天奖励与签到通知仍分别排队。违规记录批量读取纠正标记和关联处罚，JSON 关联和旧警告编号各自使用索引。

任务的管理员豁免、白名单范围、暂停行为、信任后取消行为及通知分类由 `action_specs.py` 定义，`action_policy.py` 负责当前状态核查。不同策略的差异仍明确保留，例如验证码清理独立于成员当前状态，已经完成踢出的任务仍继续解封。修改通知分类时须同步迁移已存在的 `queue_scope` 表达式。

`CallbackAnswers` 统一管理、验证码、积分和抽奖的短提示回执：业务提交后最多保留 64 个回执任务、同时请求 8 个，每个任务总等待上限 4 秒。丢失提示不重放已完成操作，关闭运行时会取消这些提示任务。前端后台轮询等待本次请求结束后再安排下一次，避免慢查询持续使旧结果失效。

消息审核调用 `message_activity.py` 计算有界的指纹和频率统计，调用 `moderation_records.py` 新增或合并违规证据，再由 `moderation_penalties.py` 按联系人、昵称、正文规则的优先级生成处罚。重复证据不重复产生处罚；新原因或新标志改变处置时仍能升级。发图门槛保持只删消息的独立策略。

`message_identity.py` 按 Telegram 身份字段统一解析直接发送者与访客机器人发起人（用户或频道）；不使用昵称、头像或兼容用的 `Channel_Bot` 推测真实所有者。外部频道直接发言、访客频道代发均进入规则、外群链接核实和独立 AI 审核。`channel_moderation.py` 用真实 ID 区分本群匿名管理员、关联频道与外部身份，在消息审核和处罚发送前核实关联关系；查询失败保留重试，不猜测身份。频道不创建普通 Member，也不调用用户禁言或用户封禁接口。

`channel_ad_penalty` 在群设置中选择只删消息或删除并封禁发言频道（默认后者）。仅在明确规则或 AI/已确认样本提供证据后生成 `channel_ad_ban`，使用 `banChatSenderChat`；这不是 Telegram 的用户入群封禁。处理前复核当前消息、启停、规则/样本版本、人工纠正和官方频道身份。违规记录支持 `channel_unban`，使用 `unbanChatSenderChat` 撤销本机器人仍有效的频道封禁，不能借用户解禁接口处理负数频道 ID。

代码块和图片说明中的网址、隐藏文字链接及当前消息自身按钮的文字/目标进入审查；URL 提取先处理全角与不可见格式字符，实体偏移仍从原文按 UTF-16 读取，路径大小写不被改写。引用消息的按钮不算回复者发送的按钮。AI 收到真实发送者昵称、链接目标与按钮内容；依赖隐藏链接或按钮的判定不自动变成可单凭普通正文复用的广告样本。编辑消息的证据摘要包含按钮、代发来源及自动转发标志，旧判定和待执行任务必须重新核实。外群链接证据只适用于当前消息仍包含的目标。

这些入口修复没有添加截图中的账号、域名或广告词；词库、词义与例外仍从 Rule/SharedPolicy 读取。当前审核没有解读纯图片、二维码、音视频内容，也不自动访问普通网页的跳转目标。规则边界检查中仅逐项更新了两个操作/接口名称显示表、一处原样 URL 正则的输入变化，以及两处频道纠正 API 的 `unban` 枚举检查；广告业务种子和三份规则适配入口保持不变。原有 URL 协议/域名解析等冻结常量仍保留，静态检查不能保证所有间接写法均无遗漏。

昵称和正文永久禁言共用成员创建、证据封装和入队流程，仍按昵称优先于正文选择任务类型，保留既有去重键。`sender_identity.py` 统一用户、频道及不完整资料的名称整理；审核、违规证据和处罚重查使用带 `@username` 的名称，归档和聊天保留纯名称及各自的字段长度。

成员禁言和恢复共用 `restriction_state.py` 的权限快照、期限及原限制归属比较，各操作仍在原有决策时机重新检查。状态表情封禁与禁言共用 `MemberRestrictions.emoji_penalty` 的资格检查、状态解析和黑名单核对，按各自限制类型恢复丢失的回执。`verification_penalties.py` 统一永久处罚涉及的活动验证查询、开始状态和完成清理；只有 Telegram 接受限制后才完成验证。管理员手动修改限制、重新入群和迟到回执等情况继续由对应业务流程处理。

`chat.py` 组装聊天模块并协调工作循环、恢复和重试。`chat_observation.py` 记录收到的消息并判断是否创建回复任务；`chat_scheduler.py` 分别处理候选批次、回复目标、参与方式和任务领取，保留按会话公平调度及连续消息合并。`chat_context.py` 负责上下文筛选、构建和冻结，`chat_receipts.py` 负责确认发送后的聊天记录、会话活动、贴纸统计、归档与来源凭据。`chat_generation.py` 负责请求准备、额度结算和生成结果复用，`chat_delivery.py` 负责文本、贴纸及部分发送成功后的恢复。各模块接收明确依赖，不持有 `GroupChat`。审核规则和模型输出检查保持独立。

聊天与删除回执通过 `Action.target_message_id` 共用精确消息查询和 SQLite 表达式索引；JSON 路径使用固定字面量，避免参数化路径导致索引失效。历史操作仍完整保留，聊天检查不再逐条扫描同群全部删除任务。`deletion_tracking.py` 统一处理删除任务入队、取消和完成时的状态投影：归档模块只更新归档，`chat_messages.py` 只更新聊天记录；`deletion_effects.py` 在此基础上协调已发送回复的撤回。创建任务的模块不直接依赖归档实现，归档模块不再修改聊天消息。

## 共用数据与查询

`management_queries.py` 为 Web 和 Bot 提供同一套记录筛选、分页、结果投影、系统统计和失败记录查询。调用方只决定页大小、筛选条件和展示方式；例如网页人工操作列表可以排除系统操作，Bot 操作记录可以展示全部记录。`record_operations.py` 统一验证与违规记录的可展示操作，列表和详情投影都包含 `allowed_operations`，Bot 与网页直接使用该列表。该列表描述记录层面的选择，提交与执行仍检查最新身份、入群批次和限制归属。操作名称、状态名称和验证失败说明统一来自 `admin_labels.py`，通知回执也使用同一来源。

管理详情查询只返回普通数据，不向 Bot 返回数据库模型，也不把有效继承规则重新构造成 ORM 对象。Bot 的规则开关、匹配方式、内容和白名单备注等修改，通过 `RuleAdministration.patch_rule`、`patch_whitelist` 提交字段变更。管理模块在同一事务中核实版本、合并当前字段并保存；重复请求先返回原结果，避免重放时把后来修改的内容并入旧请求。

`GroupConfiguration.update` 是单项与批量配置修改的共同流程，负责校验、接入重查、事务内合并、冲突检查、重复请求和操作记录。表情包增量修改仍有独立的追加、移除和清空语义。

`schemas.py` 通过 `pack_names.py` 校验表情包名称，通过 `telegram_links.py` 校验 Telegram 链接和公开频道用户名。`installation_defaults.py` 从安装数据读取初始配置。这三个模块都不依赖数据库或业务服务。ORM 默认配置由 `GroupSettings` 生成。`serialization.py` 负责 ORM 行转换，`verification_state.py` 定义活动验证状态。

## 前端与配置契约

`App.vue` 只持有会话、导航、所选群、共用群列表和本次提交的操作回执。八个 `pages/*Page.vue` 分别持有本页数据、加载状态和筛选；切换群会重新创建相关页面。群设置和规则编辑弹窗独立管理草稿与错误，不再共用一个任意类型的表单对象。

`useRecords` 共用记录分页；`query.ts` 统一北京时间范围转换；`usePreview` 共用规则预览与处置说明；`useTask` 共用请求状态和会话过期处理。`useLatestRequest` 统一忽略过期请求的数据、错误和加载状态，记录页与归档列表、详情共同使用；归档的已应用筛选和导出参数仍独立保存。`ActionTracker` 的回执独立于当前页面，查询失败后仍保留已受理的任务并继续刷新。

`ActionRequests` 在发送人工处置和邀请链接请求前保存原始请求及去重编号，按账号保存在当前浏览器标签页的会话存储中。回执丢失、超时或刷新页面后继续确认同一请求，明确拿到回执后才移除；已确认的再次操作才创建新编号。系统页和白名单页分别保存读取错误和提交错误，刷新不会清除操作失败原因。

`ActionRequests` 与 `MutationRequests` 共用 `PendingRequests` 的账号隔离、会话存储、并发去重和未知结果恢复。两种适配器分别负责意图匹配、发送格式与结果校验；保留原存储键及记录格式，旧页面保存的未确认请求可直接恢复。切换账号后旧回执不能改变当前账号的数据，也不能拿旧请求跨账号重试。

聊天任务的 `error` 字段也保留正常静默、等待和跳过的处理说明。`GroupChat.status` 按任务状态只投影真正失败和撤回失败的记录作为管理故障，Bot 与网页共同消费该结果；待处理数和预算分别表达等待与额度情况，后来的正常静默不掩盖已有故障。

Web 从需要登录的 `GET /api/catalog` 读取配置默认值、取值范围、活动验证状态、状态名称、操作名称和验证失败说明。Bot 与该接口共用后端字段描述，数值范围来自同一份 `GroupSettings` schema。前端不再维护第二套业务默认值和范围。

修改 `GroupSettings` 或管理目录后，在仓库根运行：

```powershell
& 'D:\Tools\venvs\PurrAI\Scripts\python.exe' scripts/sync_admin_contract.py --write
& 'D:\Tools\venvs\PurrAI\Scripts\python.exe' scripts/sync_admin_contract.py --check
```

该脚本生成 `frontend/src/adminApi.ts`、`frontend/src/groupSettings.ts` 和浏览器测试的 `frontend/e2e/fixtures/catalog.json`。返回模型在后端执行校验，生成的类型和接口映射来自同一份 OpenAPI。目录样本只用于模拟 API，产品运行时读取真实接口。生成的 TypeScript 只声明字段类型，不重复保存配置值。

## 结构与行为检查

`tests/test_architecture_design.py` 检查包含函数内导入的生产模块依赖无环、业务模块不反向依赖入口、配置契约同步、两端共用查询投影、配置流程复用和违规证据升级。`tests/test_architecture_consolidation.py` 检查 Web 与 Bot 的记录操作一致、通知回执共用名称，以及没有归档记录时删除任务仍会使聊天上下文失效。既有验证、处罚、重启、并发、归档、OIDC、聊天及贴纸测试继续验证实际行为。

前端类型检查、单元与浏览器测试覆盖拆分后的页面和弹窗，包括后端配置目录变更后默认值与范围直接生效。生产构建仍使用既有 `npm run build`。测试均在 Windows 与模拟接口环境执行；本次未部署或操作真实 Telegram 群。

## 通用配置与本群覆盖（2026-10-29）

`shared_policy` 保存全部群设置的通用值与通用审核规则。群设置保留完整的实际值，`groups.setting_overrides` 记录管理员已单独设置的项目；修改通用值时只同步未覆盖的项目，新接入群从通用值初始化。Bot 和 HTTP 的本群设置修改共用 `GroupConfiguration`，恢复通用设置会取消对应覆盖。

审核、处罚前复核、聊天输入、上下文和输出检查统一使用 `shared_policy.effective_rules`。通用规则与本群覆盖按稳定规则 ID 合并；本群修改通用规则时记录覆盖，未修改的群继续跟随通用规则，本群新增规则只在本群生效。迁移保留旧规则行和历史操作 ID，不删除原始规则；已有配置列表中的共有规则成为通用规则，未配置规则的群自动继承。

状态表情在入群和群内发言时检查：入群命中仍永久封禁，带消息的检查命中则执行 `emoji_status_mute`、删除对应消息并永久禁言。永久禁言沿用限制归属、管理员和白名单豁免、处罚前状态复核及丢失回执恢复。

## 架构检查后的行为修复（2026-10-30）

`rule_evaluation.py` 从只读会话取得群配置和有效规则快照，在工作线程评估消息和昵称，并预计算消息指纹。写入违规和任务之前比较快照；配置变化时重新评估。拼音和标准化匹配使用有界缓存，拼音按完整音节边界匹配，不再对每条规则重复转换正文。任务执行中的永久关键词禁言在最终限制请求之前重新检查当前有效规则，同时先恢复已经被 Telegram 接受的限制回执。

`record_versions.py` 提供内容版本，规则、通用规则的本群覆盖和白名单共用冲突检查；Web 与 Bot 提交读取时的版本，旧面板也不能覆盖后来的决定。`MutationRequests` 保存管理写入的原始内容、目标、版本与编号，覆盖规则新增、编辑、恢复、白名单及通用配置；后端把编号绑定到同一操作意图，再返回已提交结果。

运行管理层监督常驻任务并保存独立状态，身份接口与群发现解耦，HTTP 配额按登录、读取和写入分开。0023 为临时交互与已完成输入建立到期维护；归档容量按自身数据计量。具体接口约定、期限和升级操作见 [运维说明](OPERATIONS.md#管理编辑恢复与临时记录0023-起)。
