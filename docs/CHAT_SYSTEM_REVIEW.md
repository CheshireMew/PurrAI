# 聊天系统整体复核（更新至 2026-10-23）

本报告记录聊天系统本地复核，并同步对已发布版本 `833385e` 的回复等待、明确图片提问、广告过滤和关联撤回修正。覆盖入站审核、触发判断、连续消息、上下文、单次模型请求、额度、文字及贴纸发送、限流重试、重启和设置接口。此前通过只读服务器记录定位截图问题，本地修正纳入 2026-10-23 全量发布范围。没有更换模型、增加分类模型或改变聊天人设。

## 结论

保留当前单次模型调用结构。程序先过滤群内配置的正文规则和明确的广告招揽组合，模型在一次请求中判断是否广告、是否回复以及回复正文和贴纸。移除固定的 10 秒等待和聊天层额外的 8 秒间隔，明确叫机器人或回复机器人时不再因图片而直接跳过。当前提示词在已发布的 954 字符上增加图片说明、强化广告静默判断并增加布尔输出字段，默认配置下为 1146 字符，完整内容见 [提示词审阅](CHAT_PROMPT_REVIEW.md)。

当前流程为：先完成群审核 → 排除系统流量、功能口令及机械规则命中的招揽内容 → 立即处理符合条件的提问，合并已排队的同组补充 → 普通含图消息保持安静，明确提问保留有效文字和图片不可见标记 → 排除失效消息与引用 → 请求一次模型判断广告及生成结果 → 发送前重查输入和输出 → 引用原消息发送并保存回执 → 确认原消息删除时同步安排撤回。

## 已复现并修正的问题

| 原行为及影响 | 当前处理 |
| --- | --- |
| 固定等待 10 秒及聊天层 8 秒间隔使明确提问也必须等候。 | 移除这两处人为等待，保留已有接口限流和失败退避。已排队的同组补充可以合并，生成期间的补充仍可作为续聊处理。 |
| 两个人同时点名机器人，整个队列只选最后一个问题，其他问题被标成合并。被删的最后一条也会连带取消前面的正常提问。 | 同一用户的一组发言可以合并，不同用户的明确提问分别保留。先逐条剔除失效候选，再选择回复目标。 |
| 图片过滤没有区分主动插话和明确提问，@ 后引用图片也直接跳过。 | 普通含图消息组保持安静；被 @、叫昵称或回复机器人时允许回答，说明看不到图片，只依据正文和引用文字。仍按相邻发送间隔不超过 10 秒关联图片前后的连续消息，独立成员及子话题互不影响。 |
| 频道正文或图片说明已收到，但频道消息不进入普通聊天上下文，用户引用后只问“你怎么看”时可能接到旧话题。 | 频道帖子不主动触发；明确提问引用帖子时补入有效文字和图片不可见标记，优先使用最新归档文字，关闭归档时使用本次引用附带的文字。删除与违规过滤照常生效。 |
| 生成答案期间收到同一用户的补充，主动聊天关闭时可能没有入队；排队后又可能因为它早于机器人的回复而丢失。 | 同一组正在处理的请求可接收补充；通过上一次请求编号和同组关系确认续聊。别人、其他子话题以及明确回复第三人的消息不能借此进入对话。 |
| 续聊时间只判断“小于 90 秒”，负数也满足，早于机器人回复的无关消息可能被误判成续聊。 | 普通续聊需要位于机器人回复之后；只有能够关联到同组既有请求的排队补充才单独处理。 |
| “刚聊过”会绕过普通插话的广告静默检查。 | 未被直接询问的广告议论保持安静；同一用户明确问过广告问题后，正常追问可以继续，不会把“广告”整体变成禁词。贴纸不会清掉这段正常对话的状态。 |
| 不带“广告”字样的招揽可能进入聊天，模型仍进行劝告或吐槽。 | 机械过滤复用启用的正文规则，并用招揽、联系方式、业务和收益承诺的组合判断；连续拆分内容、历史缓存及发送前均检查。AI 独立输出 is_advertisement，标记广告就强制静默；缺少有效判断字段也不发送。不会由聊天过滤新增成员处罚。 |
| 开启了 `allow_sending_without_reply`，原消息已被别人删除时仍可能单独发出点评。 | 文字和贴纸均关闭该选项。Telegram 明确返回原消息不存在时取消发送，把缺失事实写回既有删除记录，使缓存与归档也能排除它；不会为记录这件事再执行一次删除。 |
| 文字发成功、贴纸被限流后，重试使用的是新整理的上下文，原答案依据的内容已经被删也可能继续发贴纸。 | 临时重试记录保留最初生成答案所用的上下文，重试仍校验它；正常新增聊天不导致重复生成或重发正文，原上下文失效就取消剩余发送。原消息不存在不会被误当成贴纸包坏了。 |
| 文字已发送，发贴纸才发现原消息不存在；任务虽然标成取消，文字却留在群内。 | 持久保存每次回复的全部发送编号及直接引用来源。确认删除后为关联文字和贴纸安排撤回，区分撤回中、已撤回和撤回失败；复用现有删除队列、限流重试和重启恢复，关闭归档、停用聊天后仍能清理。 |

关闭原消息丢失时继续发送的选项，依据 [Telegram ReplyParameters 文档](https://core.telegram.org/bots/api#replyparameters)：开启它会允许在被引用消息找不到时继续发送。

## 保留的行为

被 @、叫昵称或回复时优先处理；正常短追问及其他成员接话仍可交给模型判断。主动参与讨论继续受间隔限制，模型可以选择不回应。同群的 Telegram 子话题及不同群各自维护上下文；模型请求和 Telegram 网络发送期间不持有数据库写锁。

保留上下文条数、字符数和有效期限制，以及既有每日额度、短时调用间隔、发送前输出检查、贴纸选择和去重。明确限流可以重试，发送结果不确定时不会为了追求成功而自动再发一遍。恢复、编辑和重复事件不会重新创造一条已完成的回复。

不增加语义话题识别、第二次模型审核、长期用户画像、向量库、Agent 编排或识图服务。群昵称、人格、模型参数、贴纸包及贴纸间隔未修改。上次请求编号、是否正在正常讨论广告沿用现有群话题状态；明确提问的引用文字和回复回执复用已有字段，不增加数据库迁移。回执保留 48 小时及两分钟生成余量，完成后不继续保存临时模型结果的大段上下文。

## 实际限制

移除人为等待不等于瞬间回复，模型、Telegram 和既有接口限流仍有处理时间。后发内容可能在当前生成之后成为下一次续聊；已经成功发出的文字不会因为后来的图片或补充被自动撤回。

普通群的 [Telegram Update 接口](https://core.telegram.org/bots/api#update) 不提供一般消息删除事件，只有商业账号消息另有 deleted_business_messages。因此，用户自行撤回或其他机器人删帖后，本机器人若没有收到确切删除事实，不能承诺立即感知；本轮不新增用户账号登录、MTProto 监听或探测消息。确认删除时会清理关联回复，未发送内容取消；外部删帖通知若要即时同步，需要有可接入的通知来源。Telegram [deleteMessage](https://core.telegram.org/bots/api#deletemessage) 只允许删除发出未满 48 小时的消息，超过限制或权限不足会记录失败。机械过滤和模型判断均可能漏判，不把网络超时或不确定结果当成删除成功。

## 验证

测试使用独立临时数据库和模拟 Telegram、模型，没有向真实群发送测试消息。10 月 23 日相关后端 367 项通过，后补图片引用边界的 52 项复核通过；补齐旧版部分发送缓存兼容后，广告、引用、发送、贴纸和撤回相关 167 项通过。使用实际配置模型检查的 6 个脱敏样例均符合预期，广告招揽保持静默，正常广告咨询、闲聊和图片提问仍可回答。不同范围的运行不重复累计，详情见 [验证记录](../VALIDATION.md)。此前图片修正的前端单元、类型检查、构建及聊天设置浏览器结果保留。样例不代表所有对话都能保证模型遵循；本次全量发布前检查见 [验证记录](../VALIDATION.md)，服务器状态以本次部署记录为准。
